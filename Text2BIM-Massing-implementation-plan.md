# Text2BIM-Massing: план реализации

Создать самостоятельный Python-пакет для генерации массингов на Linux с внешним оценщиком. После проверки подключить пакет в репозиторий Маслова отдельным экспериментом. Этапы 1–5 реализованы и проверены: два независимых сквозных задания на macOS и оба задания в чистом Linux с настоящим Codex через подписку ChatGPT и оценщиком Маслова. Подтверждены Reviewer-патч, вызов Architect, сохранение отверстия и выбор оценённого кандидата. Начат этап 6: добавлены отдельный runner/config для одного здания и проверка закреплённой версии пакета. Полное сравнение на общем датасете и многозданные задачи остаются отдельной работой. Подробности — в [журнале адаптации](docs/text2bim-adaptation.md) и [отчёте проверки](docs/validation.md).

## Что сохранить и что адаптировать

**Максимально сохранять исходные фрагменты кода Text2BIM, промпты и логику взаимодействия.** Необходимые адаптации делать минимальными правками и обёртками. Каждое изменение, включая добавление, удаление, перемещение и изменение зависимостей, одновременно фиксировать в `docs/text2bim-adaptation.md`: исходный commit/фрагмент → место в нашем пакете → изменение и причина → влияние на метод → проверка и её статус. Новый код отмечать отдельно; сохранять авторство и лицензионные уведомления. После каждого этапа сверять журнал с изменениями.

Сохранить роли Enhancer, Architect, Programmer, Reviewer и исполнение кода с исправлениями; Architect вызывается по необходимости. Заменить Vectorworks/Solibri геометрией массингов Маслова и внешней оценкой. BIM и GUI не нужны. Параметризацию и NSGA-II нашего метода внутрь Text2BIM не добавлять. Это адаптированный baseline, а не точное воспроизведение статьи.

## Контракт

```python
result = generate(task, evaluator, llm, config, output_dir)
report = evaluator(massing, context)
```

- `massing`: формат Маслова — список экструзий с `polygons`, `bottom_elevation`, `top_elevation`, в метрах.
- `context`: внешние данные задачи; `report`: JSON-совместимый словарь фактической оценки.
- Конкретные метрики, цели и направления оптимизации задаются извне. Ядро не суммирует произвольные поля отчёта.
- Для `SampleMetric`/`SampleProcessor` использовать тонкий адаптер: компоненты могут ожидать разную вложенность `sample['building']`.
- Результат: архив кандидатов с отчётами, выбранный агентом оценённый кандидат, код, история, расходы и итоговый статус.

## Этапы

1. **Каркас пакета.** Зафиксировать источники, начать журнал адаптации, выделить необходимые функции геометрии Маслова и подключить один настраиваемый LLM-клиент. Остальные решения по структуре и зависимостям принять при реализации.
2. **Сцена и инструменты.** Создание/изменение контуров и экструзий, перемещение, поворот, копирование, удаление, чтение состояния. Поддержать отверстия и отдельные компоненты, стабильные ID и rollback неудачной операции. Проверить геометрию без LLM.
3. **Агентный цикл.** Перенести роли/промпты, заменить документацию инструментов. Исполнять сгенерированный код в отдельном процессе с ограничениями времени и доступных инструментов. Разделить исправление ошибки исполнения и улучшение оценённой формы. Проверить настоящую генерацию через LLM.
4. **Обратная связь.** Реализовать `build/edit → commit_candidate → evaluate → report → Reviewer → Programmer`. Дать агенту инструмент оценки. Подключить хотя бы один реальный оценщик Маслова без изменения ядра; какой именно — выбрать по доступности окружения, отдельные критерии сейчас не вводить.
5. **API/CLI и Linux.** Проверить установку и сквозной запуск в чистом Linux, затем серию независимых задач. Первая версия готова, когда реальный LLM создаёт массинг, вызывает реальный оценщик, получает отчёт и выполняет следующую попытку. Сохранять геометрию, код и трассу каждого задания.
6. **Интеграция.** Подключить зафиксированную версию пакета к актуальной ветке Маслова тонким runner/config как отдельный эксперимент. Конкретные метрики и бюджеты выбрать в конфигурации эксперимента. Исправления общих оценщиков применять одинаково к сравниваемым методам.

## Неочевидные ограничения

- В исходном Text2BIM есть ложный успех после SyntaxError; исправить при переносе. `vs.py` — заглушки, а не рабочий движок.
- Исходные промпты используют миллиметры; внешний формат — метры. Согласовать перевод единиц и семантику колец/компонентов.
- Оценка относится к неизменяемому snapshot кандидата; после изменения формы старый отчёт к ней неприменим. Финальный кандидат должен быть действительно оценён.
- Лимиты оценок, времени и LLM-вызовов конфигурируются. Все вызовы оценщика учитываются; повторный выбор из архива не запускает оценку заново. Исчерпание бюджета возвращает накопленный результат и статус.
- Физическая валидация не блокирует ядро с другим рабочим оценщиком. Перед физическими сравнениями проверить выбранный evaluator: в аудите найдены потеря компонентов, зависимость площади от вертикального смещения и повторные симуляции.
