# Согласованность checkpoints

Checkpoint связывает неизменяемую сцену с переменными и воспроизводимыми
операциями, которые действительно создали эту сцену. Отчёт evaluator
по-прежнему относится только к snapshot и внешнему context.

## Исправленные ошибки

В версии `1132703` к snapshot в середине скрипта прикладывался весь исходный
скрипт. Его хвост мог менять геометрию после commit. Воспроизведённый пример:
выбран и оценён кандидат высотой 3 м, а сохранённый исходный код строит 6 м.

Второй пример: после commit успешный скрипт добавляет alias объекта и список
данных, не меняя сцену. При восстановлении брались ранние variables, и
следующий патч завершался ошибкой отсутствующей переменной.

Оба примера реконструированы по описанию ревью. Сам файл `counterexamples.json`
не был предоставлен и не найден в workspace; он не выдаётся за изученный.
До исправления оба теста воспроизводили дефекты; проверки находятся в
`tests/test_checkpoints.py`.

## Правило завершения checkpoint

`commit_candidate()` фиксирует текущий snapshot, переменные в этой точке и
префикс журнала геометрических операций. Если попытка завершается успешно
и её финальная сцена в точности совпадает с этим snapshot, continuation-state
дополняется всеми переменными успешного скрипта. То же правило применяется
к последующему успешному скрипту, меняющему только variables.

Сравнивается полная сериализованная сцена, включая IDs и revision. Геометрия
и полученный отчёт не заменяются. Дополнительная оценка для такого завершения
не вызывается. В metadata boundary становится `script_complete`.

Checkpoint перед последующим изменением геометрии остаётся на границе
`commit`; variables из другой сцены в него не переносятся. Ошибка скрипта
не завершает checkpoint поздними variables, но ранее зафиксированные и
оценённые snapshots остаются доступны. Как и прежде, неудачная попытка
откатывает принятие сцены и переменных исполнителя целиком.

## Исходный код и исполняемый артефакт

| Артефакт | Контракт |
| --- | --- |
| `source_code.py` в каталоге кандидата | Исходные попытки Programmer для provenance. Могут содержать хвост после checkpoint; не являются программой воспроизведения выбранной сцены. |
| `checkpoint.json` | Snapshot, типизированное состояние, units, фактически выполненные геометрические операции с их аргументами и выделенными IDs, boundary и source provenance. |
| `code.py` | Малый Python-entrypoint: воспроизвести соседний checkpoint.json, проверить точное совпадение сцены и вывести массинг. |
| `selected_code.py`, корневой `checkpoint.json` | Такой же исполняемый комплект для выбранного кандидата. |
| `selected_source_code.py` | Исходный source выбранного checkpoint, отдельно от программы воспроизведения. |

В JSON-результате поле `code` теперь содержит entrypoint воспроизведения;
`source_code` — исходный текст, `checkpoint_boundary` — границу состояния.
Это изменение формата нового экспорта; старые результаты не переписываются.
Для переноса selected_code.py нужно сохранить соседний checkpoint.json.

```bash
python runs/task-01/selected_code.py > /tmp/replayed-massing.json
```

Через API:

```python
from text2bim_massing.checkpoint import replay_checkpoint

checkpoint = replay_checkpoint("runs/task-01/checkpoint.json")
massing = checkpoint.scene.to_massing()
variables = checkpoint.state
```

Replay повторяет записанные вызовы MassingTools с теми же IDs и восстанавливает
данные variables. Он не исполняет исходный LLM-скрипт, его незафиксированный
хвост или evaluator. Поэтому повторное воспроизведение не тратит LLM/оценки
и не зависит от ветвей кода, которые не относятся к выбранной сцене.
Несовпадение воспроизведённой сцены с snapshot даёт явную ошибку.

## Патчи и границы изменения

При выборе кандидата восстанавливаются его snapshot, encoded state и журнал
операций; операции отброшенной ветки не попадают в следующий checkpoint.
Programmer получает исходный source для контекста, сцену с IDs и список
реально восстановленных переменных. Список является определяющим: наличие
имени в source ещё не доказывает его существование в раннем checkpoint.

Журнал ограничен существующим `max_state_bytes` на попытку; code-worker
сохраняет прежние ограничения времени, памяти и AST. Чтение сцены не добавляет
операций в журнал. Запись журнала и завершение variables не расходуют оценки.

Роли, исходный AST-интерпретатор и промпты Text2BIM не переписывались.
Геометрические метрики, их допуски и условия будущего сравнения не менялись.
Старые численные отчёты не объявляются неверными: evaluator получал snapshot,
и submission использовал выбранную геометрию. Исправлена воспроизводимость
артефактов и продолжение исполнения после восстановления.
