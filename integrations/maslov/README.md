# Отдельный пилот в репозитории Маслова

Runner использует установленный `text2bim-massing` с runtime-кодом commit
`3cbfead4c1b6d538138f36d0a602d79a57c50a3b` и исходные оценщики Маслова на
`607ff1fcf80477787409522d93e18e42ac1436cf`. Все настройки целей, метрик,
модели и бюджетов находятся в `pilot.json`. Модель `gpt-6.1-sol` зафиксирована
явно по локальной конфигурации Codex; reasoning для пилота — `low`.

Установка в отдельном окружении:

```bash
python3.12 -m venv /tmp/text2bim-pilot-env
/tmp/text2bim-pilot-env/bin/pip install \
  'text2bim-massing[llm,maslov,mesh] @ git+https://github.com/rokerius/Text2BIM-Massing.git@3cbfead4c1b6d538138f36d0a602d79a57c50a3b'
```

Нужен установленный Codex CLI с ChatGPT login. Также принимается editable
checkout пакета, если `src/` и `pyproject.toml` совпадают с закреплённым commit;
неотслеживаемые runtime-файлы отклоняются. Тонкий runner не входит в ядро пакета.

Эти три файла можно скопировать без правок в
`massing-generation/experiments/methods/text2bim_adapted/`. Запуск из checkout
Маслова (путь Python заменить на своё окружение):

```bash
/tmp/text2bim-pilot-env/bin/python experiments/methods/text2bim_adapted/run.py \
  --maslov-repo "$PWD" \
  --dataset experiments/workspace/parametrization/zero_shot/validation/initial_samples/1028279.json \
  --output /tmp/text2bim-site-1028279-01
```

Или запустить `integrations/maslov/run.py` напрямую с абсолютным путём
`--maslov-repo`. Каталог результата должен быть пустым. Возобновления,
параллельных запусков и автоматического поиска следующего подходящего участка
в этой версии нет. Общий `experiments/run.sh` не меняется.

Вход — один JSON sample либо список rows с `id`, `site_contour` и, если есть,
`requirements`. ID одиночного файла по умолчанию — его имя без расширения;
`--sample-id` фильтрует rows. Контекст ограничен этими тремя полями: исходные
`building`, `massing`, `pred_massing` и прочие target-поля модели не передаются.
При наличии requirements поддерживается ровно одно здание с ID, который
сохраняется в результате. Многозданные задачи отклоняются до LLM-вызова.

Выход: `submit.json` с `pred_massing=[{"id": ..., "massing": ...}]`,
`report.json` с отдельными фактическими метриками и расходами, `result.json`
со статусами; в `tasks/` полный архив каждого независимого `generate`.
Сохраняются конфигурация, SHA входного файла, runner и source commits.
Выбор сохраняется также при неполном результате, если кандидат уже оценён.
Код выхода 0 — все задачи завершены, 2 — есть незавершённые задачи; ошибки
конфигурации завершаются до генерации. Цели не агрегируются в общий score.

Это диагностический пилот на реальном контуре. Два этажа — явно заданная
задача пилота; исходная геометрия здания не используется как ответ. Для rows
с собственными требованиями нужен конфиг с инструкцией следовать именно им.
Для сравнения методов ещё нужны общий датасет, одинаковые критерии, учёт
многозданных задач и бюджеты; этот runner не заявляет benchmark-совместимость
со всеми девятью общими метриками. Параметризация и NSGA-II сюда не добавлены.

Текущий конфиг требует включать весь контур в ответ Enhancer. Это необходимо
для исходного порядка передачи задания: Programmer получает ответ Enhancer,
а не исходный context отдельным обходом. Первый пилот без этого уточнения
завершился пустой сценой; все попытки перечислены в `docs/validation.md`
standalone-репозитория.

Проверенный Linux-пилот 1028279: оценённый `c0001`, `floor_count=2`,
`site_match=1`; 3 LLM-вызова, 1 оценка, 88.86 с. Footprint 560 м² полностью
внутри участка; исходный mesh-компилятор дал замкнутую mesh 3360 м³.
Подробности и первая неуспешная попытка сохранены в отчёте standalone-проекта.
