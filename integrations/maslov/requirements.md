# Эксперимент с требованиями sample

Режим `task_mode=requirements` использует собственные требования каждого
sample. В отличие от диагностического `pilot.json`, конфиг
`requirements.json` не задаёт два этажа или фиксированную высоту этажа.
Runtime Text2BIM остаётся закреплённым на `3cbfead4c1b6d538138f36d0a602d79a57c50a3b`.

## Поддерживаемая схема

Вход — одна JSON-строка либо список rows. После выбора по ID в контексте
остаются только `id`, `site_contour`, `requirements`. Target-поля строки
`building`, `massing`, `pred_massing` не передаются модели.

| Поле | Требование |
| --- | --- |
| `id` sample | Обязателен в списке rows; для одиночного файла может быть взят из имени файла. |
| `site_contour` | Непустой валидный список колец, координаты в метрах, семантика Маслова. |
| `requirements` | Ровно одно здание. Несколько зданий не поддерживаются и отклоняются. |
| `requirements[0].id` | Непустая строка либо integer, включая 0. Тип и значение сохраняются в submission. |
| `n_floors` | Положительное целое число, включая JSON `14.0`. Дробная этажность не поддерживается исходной метрикой подсчёта этажей. |
| `floor_height` | Положительное конечное число, метры. |
| `total_area` либо `usable_area` | Положительное конечное число, м² суммарной площади этажных срезов. Это не footprint и не объём. |

Функциональные поля requirements сохраняются. Boolean, числовые строки,
NaN/Infinity, пропущенные и неположительные числовые цели не принимаются.
В схеме Маслова ноль может означать неизвестное значение; этот режим не
подставляет для него скрытые defaults. Нужно выбрать полностью заданные
samples либо отдельно согласовать общее правило defaults для обоих методов.

Алиас площади приводится исходной функцией
`subtractive_additive_massing.brief.with_canonical_area` из закреплённого
checkout. При конфликте `total_area` и `usable_area` возникает ошибка.
Оригинальный `BuildingBrief` вычисляет высоту как `n_floors * floor_height`
и среднюю площадь этажа как `total_area / n_floors`. Эти производные значения
передаются в текст задания, а исходные и нормализованные поля сохраняются.
Поиск, параметризация и деление участка из метода Маслова не вызываются.

Помимо HEAD и `src/`, runner проверяет неизменность двух используемых файлов
`subtractive_additive_massing/brief.py` и `__init__.py` относительно pin.

## Подготовка без LLM

Установка пакета и Codex для последующего живого запуска — в
[README интеграции](README.md). Для подготовки сам LLM-клиент не создаётся,
проверка авторизации и сетевые вызовы модели не выполняются.

В закреплённом checkout есть доступный реальный CoMa sample 1627:

```bash
python integrations/maslov/run.py \
  --config integrations/maslov/requirements.json \
  --maslov-repo /path/to/massing-generation \
  --sample /path/to/massing-generation/experiments/sandbox/subtractive_additive/inputs/coma_1627_single.json \
  --output runs/requirements-1627-prepared \
  --prepare-only
```

Для этого sample из данных разрешаются 14 этажей, 3.714 м на этаж,
24 806.020334769833 м² общей площади, высота 51.996 м и средняя площадь этажа
1771.8585953407023 м². Номер здания — integer `0`.

Подготовка проверяет все выбранные rows и metric factories до первого
LLM-вызова. Создаются:

| Файл | Содержание |
| --- | --- |
| `preparation.json` | Статус `prepared`, число samples и режим. Это не результат генерации. |
| `task_bindings.json` | Исходные и эффективные requirements, source paths, единицы в названиях целей, формулы, отсутствие defaults и разрешённые цели каждого sample. |
| `runner_config.json` | Полный конфиг эксперимента. |
| `experiment_provenance.json` | Package/Maslov commits, SHA точных прочитанных bytes dataset и runner, выбранные IDs. |

Обнаруженная ошибка второй строки отклоняет запуск до генерации первой.
Неподдерживаемые задачи не отбрасываются молча.

## Генерация и метрики

Повторить команду без `--prepare-only` с новым пустым `--output`.
Клиент, роли, исполнитель и архив используются из прежнего runtime Text2BIM.
Enhancer должен включать полный контур, единицы и требования в ответ Programmer.
Обход этой роли не добавляется.

| Исходная метрика | Смысл отчёта и цель конфига |
| --- | --- |
| `FloorCountError` | Относительная ошибка этажности; стремиться к 0. Используется исходный default `rounding_mode=ceil`. |
| `UsableAreaError` | Относительная ошибка суммарной площади этажных срезов; стремиться к 0 с учётом численной точности. |
| `SiteMatch` | Доля predicted footprint внутри участка; цель 1. |
| `IdIoU` | Совпадение множества IDs требований и ответа; цель 1. |

Все четыре компонента вызываются из исходного `src/sample_metric/` без правок.
Floor height и target area берутся из эффективных requirements конкретного
sample, а не из констант конфига. Общий score не создаётся.

В `tasks/<index>/task.json` находится эффективное задание, в
`task_binding.json` — его происхождение. Submission содержит нормализованные
requirements и выбранный массинг с исходным ID. Ошибки, budgets и незавершённые
результаты сохраняются, как в обычном runner.

Тесты проверяют два независимых sample с разными целями, отдельный Reviewer-патч
после реального ненулевого отчёта, алиас площади, отказ неполного ввода,
сохранение типов ID, отверстия/компоненты и инвариантность метрик к вертикальному
переносу. Живые результаты отдельно перечисляются в
[отчёте валидации](https://github.com/rokerius/Text2BIM-Massing/blob/main/docs/validation.md).

## Что остаётся

Для одного массинга полный CoMa split не требуется и сейчас не подключается. Доступный sample подтверждает путь работы
с реальными requirements, но не является сравнением на датасете.
Многозданные задачи, единое правило недостающих требований, остальные общие
метрики и общий сравнительный отчёт остаются отдельной работой.

Живой Linux-прогон 1627 выполнен: выбран c0001, floor_count_error=0,
usable_area_error≈1.47e-16, site_match≈1, id_iou=1; 3 LLM-вызова, 1 оценка,
110.87 с. Первая попытка только прочитала сцену и завершилась без кандидата.
Оба исхода и точные значения приведены в отчёте валидации.
